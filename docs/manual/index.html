01 / El punto de partida

Un buen pedido empieza
por el resultado.

Conversá con el agente principal en Codex, dentro del proyecto con Lufy instalado. Contale lo que buscás y el contexto que importa. El agente puede completar detalles con las fuentes del proyecto.

A

Qué querés obtener

Una explicación, una corrección, una propuesta, un documento o algo que funcione.

«Encontrá por qué se repiten las ventas».
B

Sobre qué trabajar

El proyecto, una ruta, un archivo, datos o material que el agente pueda consultar.

«Usá este reporte y estas consultas».
C

Qué límites importan

Restricciones reales: conservar un contrato, trabajar localmente o terminar con un análisis.

«Sólo lectura; explicá la causa».
↳

Son pistas para conversar, no un formulario obligatorio. Podés empezar con un pedido corto. El principal pregunta cuando falta una decisión material y puede avanzar con lo que no dependa de ella.

    03 / Quién participa de verdad

    Un principal a cargo.
    Ayuda cuando aporta.

    Los personajes pertenecen al universo visual de Lufy. Acá representan participantes y recursos; no son un catálogo de agentes instalados ni una cadena de roles obligatoria.

    VOS / DIRECCIÓN

    Elegís el destino y las decisiones materiales.

    Explicás el resultado y las restricciones. Intervenís cuando hace falta resolver producto, alcance o acceso, y autorizás la entrega o las operaciones externas cuando correspondan. No necesitás dirigir cada archivo o prueba.

    01
    PRINCIPAL / RESPONSABILIDAD

    Conserva el contexto y comprueba el conjunto.

    Investiga, diseña, escribe, implementa y revisa según el pedido. Elige la próxima acción, informa avances, consulta lo que no puede resolver e integra cualquier trabajo delegado. Puede hacer todo inline.

    02
    SUBAGENTE / COLABORACIÓN POSIBLE

    Resuelve una tarea independiente y acotada.

    Existe sólo si el host ofrece herramientas reales y la delegación está permitida. Recibe objetivo, contexto mínimo, permisos, ownership y aceptación. Sus resultados vuelven al principal; su autorreporte no acredita éxito por sí solo.

    03
    SKILLS Y HERRAMIENTAS / CAPACIDADES

    Aportan instrucciones o acciones concretas.

    Una skill es una guía que el agente lee cuando resulta pertinente. Una herramienta permite observar o actuar dentro de los permisos del host. Usar una skill no crea un subagente; ninguna de las dos amplía la autorización recibida.

    04

    Las cinco skills distribuidas

    Capacidades que acompañan el trabajo.

    El registry local permite resolver sus rutas. El principal elige las pertinentes; no tiene que invocarlas todas ni seguir una secuencia fija.

    lufy-checkComprobar el resultado+

    Ayuda a elegir evidencia pertinente: comportamiento para código, fuentes para investigación, fidelidad para texto, consultas para datos y estado posterior para operaciones. Puede usarla el mismo ejecutor. Leer la skill ↗

    lufy-mem-searchRecuperar contexto útil+

    Busca decisiones o aprendizajes con consultas cortas. Devuelve pistas compactas y las contrasta con archivos e instrucciones actuales. La memoria es contexto, no evidencia superior. Leer la skill ↗

    lufy-mem-captureConservar un aprendizaje+

    Captura una decisión, regla o aprendizaje durable cuando el proyecto usa memoria Obsidian. Una corrección importante puede merecer una nota; cada turno rutinario, no. Leer la skill ↗

    lufy-mem-connectRelacionar notas existentes+

    Conecta notas con destinos reales y backlinks válidos. No inventa relaciones ni vuelve más fuerte una afirmación que sus fuentes. Leer la skill ↗

    lufy-mem-documentDocumentar una decisión+

    Convierte decisiones y flujos durables en conocimiento reutilizable. Conserva motivos, fuentes y límites; puede usar capture y connect, sin obligar a pasar por todas las skills. Leer la skill ↗

    04 / Explorar la colaboración

    ¿Todo inline
    o tareas en paralelo?

    Después de cerrar las decisiones compartidas, una funcionalidad podría dividirse entre módulos independientes. El principal conserva la integración y comprueba el resultado reunido.

    Cómo se conversa con una tarea delegada +

    Intercambio ilustrativo · sólo cuando la delegación corresponde

    1. Principal → tarea A

      «Construí la interfaz sobre el contrato acordado. Tus archivos son los del módulo A. Conservá el resto y reportá cambios, comprobaciones y límites. Sin acciones Git».

    2. Principal → tarea B

      «Implementá el servicio del módulo B según el mismo contrato. Trabajá sólo en tus archivos. Indicá qué verificaste y qué queda pendiente. Sin modificar el contrato compartido».

    3. Tareas → principal

      Devuelven su resultado y evidencia. Por ejemplo: «El cambio local está aplicado; esta comprobación no pudo ejecutarse por falta de una dependencia». Lo pendiente conserva su estado.

    4. Principal → vos

      Integra, inspecciona los cambios y comprueba el recorrido conjunto. La respuesta final distingue lo observado de lo pendiente; no declara éxito sólo porque las tareas dijeron «listo».

    Diagrama de una colaboración posible, no un scheduler automático. Si las tareas comparten archivos o dependen de una decisión abierta, primero se reorganiza el trabajo. La delegación nunca concede permisos nuevos.

    05 / Llegar a puerto

    Terminar es poder explicar
    qué quedó resuelto.

    Una respuesta útil conecta el resultado con su evidencia y deja visibles los límites. El formato se adapta al pedido; no hay un reporte universal obligatorio.

    01

    Resultado

    Qué se entendió, decidió, escribió, construyó o recuperó. Una propuesta puede estar terminada aunque no se implemente.

    02

    Evidencia

    Qué fuentes o comprobaciones sostienen lo dicho. Ejecutar un comando, guardar un registro o decir «listo» no prueba su efecto.

    03

    Límites

    Qué no se pudo comprobar, qué decisión falta o qué acción requiere autorización. Un resultado inconcluso se informa como tal.

    ⚑

    ¿Y commit, push, PR o publicación?

    Son acciones de entrega que deben estar cubiertas por autorización explícita. Si el pedido las incluye, el principal continúa con sus controles y observa los checks remotos pertinentes. Resolver el código no implica publicar automáticamente.

    Antes de tu próximo pedido

    Dudas de navegación.

    ¿Tengo que nombrar roles o elegir una metodología?+

    Pedí el resultado que necesitás. El flujo inline no exige tiers, una cadena de roles, una metodología ni envelopes para avanzar. Los nombres de agentes disponibles dependen del host; el catálogo actual de Lufy no instala esos roles.

    ¿Tengo que decir qué skill usar?+

    El principal puede elegir una skill pertinente a partir de su descripción y el pedido. También podés solicitar una skill disponible explícitamente. Leerla orienta una acción; no reemplaza el juicio ni garantiza el resultado.

    ¿Cuándo me va a preguntar?+

    Cuando falte una decisión material de producto, alcance o acceso que no pueda resolver con el contexto disponible. Puede seguir con trabajo independiente. El silencio no autoriza las acciones que dependan de la respuesta.

    ¿La memoria y el contexto se usan siempre?+

    Se usan cuando aportan valor y están disponibles. El hook instalado orienta el inicio de sesión y puede refrescar el registry de skills; no registra conversaciones ni captura todas las decisiones. El grafo es lexical y la memoria puede estar desactualizada: se contrastan con fuentes actuales.

    ¿Qué pasa si una prueba falla o falta acceso?+

    El principal diagnostica y corrige dentro del alcance. Si no puede avanzar por una dependencia, permiso o decisión, informa el bloqueo concreto y la recuperación necesaria. Las comprobaciones afectadas se repiten después de cambiar su fuente; una comprobación omitida no se presenta como aprobada.

    ¿Estos ejemplos prueban cómo respondió un modelo real?+

    Son recorridos didácticos, escritos para explicar el comportamiento previsto por las políticas actuales. No son trazas, benchmarks ni resultados reales. La respuesta concreta depende del pedido, las fuentes, las herramientas y los permisos disponibles.

    ¿Cómo abro o comparto este manual?+

    Está versionado en docs/manual/. Abrí index.html con sus archivos y assets dentro del checkout, o serví la raíz como sitio estático. GitHub muestra el código HTML; subirlo al repositorio no crea un hosting público. La guía técnica tiene las instrucciones. Cómo abrirlo y mantenerlo ↗
