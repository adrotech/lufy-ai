# Diseño

El sidecar liga evidencia al candidato comprometido HEAD, no a un snapshot sintético del worktree. La CLI captura JSON por stdout; el usuario/host lo guarda fuera del candidato. Verify recibe sidecar, base y evidencia, valida el claim mediante políticas existentes y compara todos los campos calculados de nuevo. La igualdad no autentica autoría ni demuestra que comandos declarados realmente se ejecutaron; detecta obsolescencia relativa al snapshot declarado.

`candidateevidence` obtiene identidad de repositorio hasheando el git-common-dir canónico, resuelve base/HEAD como commits y árboles, y hashea diff raw NUL con paths, modos y object IDs. No almacena rutas privadas ni texto de evidencia. La reubicación del repositorio invalida conservadoramente la identidad. Lee políticas `.lufy/contracts/delivery.md`, `.lufy/contracts/result-contract.md` y presencia/contenido de `.lufy/config/project.yaml`, rechazando symlinks/no regulares. Los hashes separan componentes con estructura canónica.

Git se invoca con argv literal, deadline de observación de 10s, WaitDelay de cleanup de 1s y salida bounded, sin shell, optional locks, fsmonitor, external diff ni textconv. Antes de resolver objetos se leen nombres de config y se rechazan partial clones/promisors; GIT_NO_LAZY_FETCH=1 evita fetch implícito. Antes de status se leen sólo nombres de claves de config y se rechaza cualquier filter.* efectivo, incluidos includes locales. Se rechazan gitlinks 160000 antes de cualquier recursión. Estas limitaciones conservadoras evitan callbacks en filtros/submódulos; no prometen un lock contra mutación hostil concurrente de configuración. Se eliminan overrides GIT_DIR/WORK_TREE/INDEX/config de entorno que desviarían el target; no se escribe índice ni objetos. Se exige limpieza tracked y untracked, con única excepción exacta de project.yaml ligada por hash. Los internos locales adicionales requieren un checkout limpio aparte; nunca se ocultan fuentes nuevas por prefijos amplios. Se vuelve a observar identidad/limpieza/política para detectar cambios durante la captura; esto no proporciona un lock contra cambios posteriores, por eso verify debe ejecutarse inmediatamente antes del consumo.

La CLI reutiliza decoder/canonicalización/evaluación de claim existentes. El sidecar es JSON estricto bounded, rechaza claves duplicadas/unknown, trailing data y valores mal formados. No tiene estados ni receipts; result-transition/v1 sigue siendo la única autoridad de gates. El bloque 4 conserva su productor sin inferir un binding retroactivo.
